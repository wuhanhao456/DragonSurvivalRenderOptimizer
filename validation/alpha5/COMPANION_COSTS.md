# 整包热点的独立分析

本页来自修改前的 alpha.4 服务器场景诊断。它解释本轮优先级，不能用来计算 alpha.5 性能提升；没有新增持续监测，也没有修改实际整包的 FancyMenu/KubeJS 配置。

当时使用 i7-13700K、RTX 5070 Ti、Java 21.0.8、16 GiB 堆、Complementary Unbound r5.9。JFR 约 45 秒，另一个不含该录制的计数区间约 86 秒。两段不同步，阶段计时有包含关系，不应相加成整帧占比。

| 原诊断 | 结果 | 本轮处理 |
| --- | --- | --- |
| DS 皮肤生成和 GPU 回读 | 都为 0 | 保留已工作的纹理路径 |
| DS GPU 通道 / 绘制 | 55 / 53 次每帧 | 减少兼容批次的上传与绘制 |
| 附近末 NPC | 4 个在 32 格内；原版走 Gecko CPU 几何 | 可选 GPU 适配，另测地黄龙 |
| 渲染线程分配 | 周期计数约 703 MiB/s | 减少顶点和矩阵临时对象 |
| Gecko `createVerticesOfQuad` 分配 | JFR 校正估计约 167 MiB/s | 默认几何的 CPU 临时存储复用 |
| FancyMenu `PoseStack` 分配 | JFR 校正估计约 49 MiB/s | 不改菜单配置或骨骼钩子，单独留作后续排查 |
| KubeJS HTTP 线程分配 | 周期计数约 125 MiB/s | 独立服务成本，不算 DSRO 收益 |
| 16 次 GC 暂停 | 合计约 73 ms，最大约 12 ms | 可能影响尾帧，不能独自解释持续低 FPS |

JFR 已排除每线程首次分配权重，避免把录制前累积量误算进这 45 秒。执行样本没有虚调用接收对象，不能把全部通用 Gecko 栈都归因给末。Xaero 的顶点包装器还参与图标检测；DSRO 保持特殊消费者的 CPU 路径，不直接移除它。

FancyMenu 若要继续优化，应先确认无附加变换时的快速返回条件、菜单和世界渲染语义，再单独配对测量。KubeJS 热点是 `tinyserver.HTTPServer.run` 的 NIO 接收循环，不能称为服务器游戏脚本开销；是否关闭网页服务应另行决定和测试。二者均不列为 DSRO 的依赖，也不纳入本轮收益。

不公开真实服务器地址、聊天记录、账户、启动参数或原始 JFR；完整私有诊断保留在本地。
